# ⚙️동시성 제어
> 여러 사용자나 프로세스가 데이터를 공유할 때 발생할 수 있는 문제를 해결하기 위해, 
데이터베이스 시스템이 트랜잭션을 순서대로 실행하는 것이 아닌 동시에 실행될 수 있도록 허용하여, 데이터의 **일관성**보장과 **무결성**을 유지할 수 있도록 함.
--
 ## ⚠️ 동시성 제어 미비 시 발생할 수 있는 문제들

### 1️⃣ 분실된 갱신 (Lost Update)
> 두 개의 트랜잭션이 **같은 데이터를 동시에 갱신**할 때,  
> 한 트랜잭션의 결과가 **다른 트랜잭션에 의해 덮어써지는 경우**

**💬 예시**
- 트랜잭션 A와 B가 동시에 동일한 사용자의 포인트를 수정  
- A가 `+100` 후 커밋 전에 B가 `+50`을 수행 → **B의 결과로 A의 갱신 내용이 사라짐**

```text
A: 포인트 읽기 → 100
B: 포인트 읽기 → 100
A: 100 + 100 = 200
B: 100 + 50 = 150
A 커밋 → 200 저장
B 커밋 → ❌ 150으로 덮어씀 (A의 결과 분실)
```
---
### 2️⃣ 모순성 (Inconsistency)

> 두 개 이상의 트랜잭션이 동시에 실행되어
> 데이터 간의 일관성이 깨지는 경우

**💬 예시**
- A 계좌 잔액: `100,000원`
- 동시에 두 개의 트랜잭션 발생
  1. 트랜잭션 A → `5만 원 출금`
  2. 트랜잭션 B → `2만 원 입금`

| 시점 | 트랜잭션 A (출금) | 트랜잭션 B (입금) | 잔액 결과 |
|------|--------------------|--------------------|------------|
| T1 | 잔액 조회 (10만 원) |  | 10만 원 |
| T2 |  | 잔액 조회 (10만 원) | 10만 원 |
| T3 | `10만 - 5만 = 5만 원` 으로 수정 |  | 5만 원 |
| T4 |  | `10만 + 2만 = 12만 원` 으로 수정 | ❌ 실제로는 7만 원이어야 함 |

> 💥 문제: 두 트랜잭션이 동시에 실행되어,  
> 서로의 작업 결과를 반영하지 못한 채 잘못된 잔액(12만 원)이 기록됨.
---
### 3️⃣ 연쇄 복귀 (Cascading Rollback)

> 여러 트랜잭션이 같은 데이터를 갱신하는 중에
> 하나의 트랜잭션이 실패하면,
> A가 실패하여 롤백되면,
  B는 **잘못된 데이터를 사용했기 때문에 같이 롤백**되어야 함
---
### 4️⃣ 비완료 의존성 (Uncommitted Dependency)
> 한 트랜잭션이 **아직 커밋되지 않은 다른 트랜잭션의 결과를 참조할 때** 발생
> 이후 그 트랜잭션이 실패하면 **잘못된 데이터를 기반으로 한 오류 전파** 발생

**💬 예시**
- 트랜잭션 A: 사용자 포인트를 +500 업데이트 (아직 커밋 전)
- 트랜잭션 B: A의 갱신 결과를 읽고 새로운 계산 수행
- A가 롤백되면 B는 존재하지 않는 데이터를 바탕으로 동작한 꼴

---
### 🧭 정리
| 문제 유형       | 원인                         | 결과                |
| ----------- | -------------------------- | ----------------- |
| **분실된 갱신**  | 동일 데이터 동시 갱신               | 한 트랜잭션의 결과가 덮어써짐  |
| **모순성**     | 동시에 다른 트랜잭션이 데이터 변경        | 데이터 일관성 붕괴        |
| **연쇄 복귀**   | 실패한 트랜잭션의 데이터를 다른 트랜잭션이 참조 | 연쇄적인 롤백 발생        |
| **비완료 의존성** | 커밋되지 않은 데이터 참조             | 오류 전파 및 잘못된 결과 발생 |

> 💡
> 동시성 제어는 여러 사용자가 동시에 DB를 사용할 수 있도록 허용하면서도
> 데이터의 신뢰성과 정확성을 지키기 위한 핵심 기술

## ✅ 동시성 제어 방법

### 🔒 1.Lock (잠금)
- 한 트랜잭션이 데이터를 수정하는 동안 **다른 트랜잭션이 접근하지 못하게 막는 방법**
- 단일 스레드 또는 단일 프로세스에서만 동작, **한번에 하나의 스레드만** 공유자원에 액세스
``` text
트랜잭션 A가 잔액을 수정 중이면, B는 A가 끝날 때까지 대기
```
- 기본적으로 lock연산과 unlock 연산을 사용
- Lock을 걸거나 해제 시점에 제한을 두지 않으면 두 개의 트랜잭션이 동시에 실행되어 데이터 일관성 깨질 수 있음
- 신뢰성과 안정성이 높으며, 어떤 수준의 locking을 적용하느냐에 따라 교착 상태나 경쟁 조건과 같은 문제를 방지할 수 있다.
- Lock의 종류

| 종류       | 주요개념                         |
| ----------- | -------------------------- |
| **공유 Lock (Shared Lock)** | - 해당 트랜잭션은 데이터 항목에 대해 **읽기(Read)**만 가능<br>- 다른 트랜잭션도 **읽기(Read)**만 수행할 수 있음<br>➡️ **동시 읽기 가능, 쓰기는 불가** |
| **전용 Lock (Exclusive Lock)** | - 해당 트랜잭션은 데이터 항목에 대해 **읽기(Read)**와 **기록(Write)** 모두 가능<br>- 다른 트랜잭션은 **읽기(Read)** 및 **기록(Write)** 모두 불가능<br>➡️ **완전한 독점 접근** |
    
>  ` 블로킹(Blocking) 현상  `    
> - Lock 간 경합이 발생하여 특정 트랜잭션 작업을 진행하지 못하고 멈춘 상태  
> - 공유 Lock과 전용 Lock 또는 전용 Lock과 공유 Lock 끼리 블로킹이 발생할 수 있음  
> 즉, **블로킹을 최소화**해야함   
` 교착 상태(DeadLock)  ` 
> - 두 트랜잭션이 각각 Lock을 설정하고 서로의 Lock에 접근하여 값을 얻어오려할 때   
> 이미 각 트랜잭션에 의해 Lock이 설정되어 있어 트랜잭션이 영원히 처리가 되지않는 상태

#### ⚠️ 단점   
- 동시성 처리 속도가 저하될 수 있고, 대기 시간이 발생할 수 있다.   

### 🕒 2. 타임 스탬프(Time Stamp)   
> 트랜잭션이 시스템에 진입한 **순서대로 고유한 시간 스탬프(Time Stamp)** 를 부여하여  
> 이를 **동시성 제어의 기준**으로 사용하는 방식입니다.

> 💡 즉, “누가 먼저 왔는가”를 기준으로 트랜잭션의 실행 순서를 결정합니다.

#### 🧭 타임 스탬프 부여 방식

| 구분 | 내용 |
|------|------|
| **System 시계 사용법** | 트랜잭션이 시스템에 들어올 때의 **시스템 시계(System Clock)** 값을 시간 스탬프로 지정 |
| **논리적인 계수기 사용법** | 시스템이 유지하는 **계수기(Counter)** 값을 사용하여, 트랜잭션이 들어올 때마다 1씩 증가시켜 스탬프 부여 |
   
**💬 예시**

| 트랜잭션 | 부여된 타임 스탬프 | 실행 순서 |
|-----------|------------------|------------|
| T1 | 1001 | 먼저 실행 |
| T2 | 1002 | 나중 실행 |

> 🧩 **원칙:** 타임 스탬프가 **작은 트랜잭션이 먼저 실행**된 것으로 간주되어  
> 나중에 들어온 트랜잭션(T2)은 T1의 작업을 침범할 수 없습니다.

### ✅ 3. 적합성 검증 (낙관적 검증 기법, Optimistic Concurrency Control)
  
트랜잭션이 실행되는 동안 **잠금(Lock)을 걸지 않고 자유롭게 수행**한 뒤,  
**종료 시점에 검증(Validation)** 을 통해 데이터 충돌 여부를 확인하고  
문제가 없을 경우 **커밋(Commit)** 하는 방식입니다.

> 💡 “충돌이 자주 일어나지 않는다”는 낙관적인 가정(Optimistic Assumption)에 기반한 제어 기법입니다.

#### 🔍 특징

- 트랜잭션 수행 중에는 **검증을 하지 않음**  
- 종료 시점에 **적합성 검증(Validation Phase)** 을 통해 다른 트랜잭션과의 충돌 여부 판단  
- **충돌 시 → Rollback** 수행  
- 트랜잭션이 길거나 충돌이 많으면 **자원 낭비** 발생  
- **동시 접근 빈도가 낮은 환경**에서 효율적


#### ⚙️ 트랜잭션 처리 단계

| 단계 | 설명 |
|------|------|
| **① 읽기 단계 (Read Phase)** | 트랜잭션이 데이터를 읽고 자신의 작업 공간(버퍼)에서 처리 |
| **② 검증 단계 (Validation Phase)** | 트랜잭션 종료 시점에 다른 트랜잭션과의 충돌 여부 검사 |
| **③ 기록 단계 (Write Phase)** | 검증 통과 시 실제 데이터베이스에 반영(Commit), 실패 시 Rollback |

#### ⚠️ 단점
- 트랜잭션이 길고, 검증 단계에서 실패하면 **전체 작업을 되돌려야 하므로 자원 낭비** 발생  
- 따라서 **트랜잭션 충돌이 드문 환경(예: 분석용 시스템)** 에서 주로 사용

#### 🧭 정리

| 구분 | 타임 스탬프 기법 | 적합성 검증 기법 |
|------|------------------|------------------|
| **기준** | 트랜잭션 진입 시간 (Time Order) | 트랜잭션 종료 시 검증 |
| **제어 방식** | 순서 기반 제어 | 사후 검증 기반 제어 |
| **장점** | 순서 보장, 충돌 방지 | 락 사용 X → 높은 동시성 |
| **단점** | 충돌 시 재시도 필요 | 검증 실패 시 자원 낭비 |
| **적용 환경** | 일반 트랜잭션 처리 시스템 | 동시 사용 빈도 낮은 시스템 |

---  

### ⚙️ 4. MVCC (다중 버전 동시성 제어, Multi Version Concurrency Control)

> MVCC는 데이터베이스가 **동시에 여러 트랜잭션이 접근하더라도 충돌 없이 처리**할 수 있도록  
> 데이터를 **여러 버전(Multiple Versions)** 으로 관리하는 **동시성 제어 기법**
> 즉, 데이터 업데이트 시 기존 내용을 덮었는 것이 아닌 **새로운 버전을 만드는 것**.

- 각 트랜잭션은 자신이 시작한 **시점의 데이터 스냅샷(snapshot)** 을 읽는다.  
- 다른 트랜잭션이 데이터를 수정하거나 커밋 중이더라도,  
  해당 트랜잭션의 **변경사항은 커밋 완료 전까지 보이지 않는다.**
- 데이터 수정 시 기존 데이터를 덮어쓰지 않고,  
  **UNDO 영역에 새로운 버전의 데이터**를 생성하여 관리한다.
- 즉, 각 트랜잭션은 자신만의 “시간대별 데이터 버전”을 읽으며  
  이를 통해 **직렬 가능성(Serializability)** 을 보장한다.

**💬 예시**

```text
1️⃣ 트랜잭션 A가 시작 → 현재 데이터(버전 1) 조회
2️⃣ 트랜잭션 B가 같은 데이터를 수정 → 버전 2 생성 (아직 커밋 X)
3️⃣ A는 여전히 버전 1을 읽음 (B의 변경 내용은 보이지 않음)
4️⃣ B 커밋 완료 후, 새로운 트랜잭션 C는 버전 2를 읽게 됨
```

> 💬 트랜잭션마다 **독립적인 버전**을 읽기 때문에  
> **읽기 작업이 쓰기 작업에 의해 블로킹되지 않음** → 빠른 동시 처리 가능!

---

#### ⚙️ MVCC의 주요 특징

| 구분 | 설명 |
|------|------|
| **동시성 향상** | 트랜잭션이 읽기 시 Lock을 걸지 않아도 되므로 대기 시간 감소 |
| **데이터 일관성 유지** | 각 트랜잭션은 자신이 시작할 때의 데이터 스냅샷을 기준으로 일관된 결과를 얻음 |
| **버전 관리 방식** | 데이터를 덮어쓰지 않고 새로운 버전 생성 (Undo Log 또는 Undo Segment 사용) |
| **읽기/쓰기 분리** | 읽기 트랜잭션은 이전 버전을 읽고, 쓰기 트랜잭션은 새 버전을 작성 |

---

#### ⚠️ 단점 및 주의사항

- ❗ **사용하지 않는 데이터 버전(Old Version)** 을 정리하는 **Garbage Collection** 필요  
- ❗ **데이터 버전 충돌** 발생 가능 (예: 동일 행의 다중 갱신 시)  
- ❗ **Undo 블록, I/O 부하 등 추가적인 오버헤드** 발생 가능  

---

#### 🧭 요약 정리

| 구분 | 내용 |
|------|------|
| **기본 개념** | 각 트랜잭션이 고유한 데이터 스냅샷을 읽는 방식 |
| **장점** | 트랜잭션 대기 시간 없음, 높은 동시성, 읽기/쓰기 분리 |
| **단점** | 버전 관리 오버헤드, 데이터 정리(GC) 필요 |
| **적용 예시** | PostgreSQL, Oracle, MySQL(InnoDB) 등 |

> 💡 **MVCC는 “읽기-쓰기 병행성”을 극대화하는 현대 DBMS의 핵심 기술**

### ✅ 동시성 제어 기법 비교 정리

| 기법 이름 | 장점 | 단점 |
|------------|-------|------|
| **Locking 기법** | ① 데이터 오류를 사전에 예방<br>② 구현이 비교적 단순 | ① Lock 대기로 동시성 저하<br>② 교착 상태(Deadlock) 발생 가능 |
| **Time Stamp 기법** | ① 교착 상태 없음<br>② 대기 시간 없음 | ① Rollback 발생 확률 높음 |
| **적합성 검증 (낙관적 제어)** | ① 높은 동시 처리 능력<br>② 대기 시간 없음 | ① 장기 트랜잭션 실패 시 자원 낭비 |
| **MVCC (다중 버전 제어)** | ① 대기 시간 없음<br>② 다른 트랜잭션 수정에 영향받지 않음 | ① 불필요한 버전 정리 필요<br>② 버전 충돌 가능<br>③ 추가 오버헤드 발생 |
